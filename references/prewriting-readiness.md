# Prewriting Readiness Loop

Use this reference for a serious new long-form project or a foundational rebuild. It owns **pre-draft convergence and formal draft permission**. Its machine-readable record plus deterministic checker are the sole permission authority; other owners supply evidence and prose reviews explain it. Project Doctor `0 errors / 0 warnings` proves structural health only.

The readiness system is **Base + activated protections**, not a fixed literary ontology or ten-document bureaucracy.

### Conditional literary maturity

Assess maturity against current Project Poetics, using its four-axis organizing compilation. The existing Project Poetics / Narrative Strategy maturity evidence may carry `draft_dependencies`: a list with unique `id`, boolean `required_for_draft`, project-specific `reason`, and operational `handling` (`decided`, `preserve-open`, `not-applicable`, `unresolved`). Decided and preserve-open records require an `evidence_ref`; preserve-open also requires a substantive `compatibility_boundary` and must not be a choice whose decided answer is required for drafting. These are evidence dispositions, not narrative modes or scores. Legacy evidence remains readable; the planner must assess current consequential choices rather than claim an empty list proves maturity.

A promised uniquely solvable mystery needs its solution and clue accessibility decided. A confession needs its narrator/voice regime if drafting depends on that choice; a memory-led work needs temporal links and recurrence anchors. An action work can mark obsession architecture not applicable. A deliberately open metaphysical question can remain open when the current-volume compatibility envelope is stable and future scenes can safely honor it. An undecided answer actually needed to write the volume still blocks. This layer never weakens complete first-volume architecture, later-volume direction, live context identity or author approval.

For substantial new projects, maintain the thin machine-readable gate record from `assets/prewriting-templates/prewriting-readiness-template.json` and verify it with `scripts/prewriting_readiness.py`. The record stores operational decisions and evidence refs only; it does not schema literary meaning.

## 0. Upstream Project Brief

Complete the adaptive intake in `front-loaded-adaptive-intake.md` before substantial architecture or drafting. The Project Brief is the upstream record of explicit user intent, delegation, absence/prohibition, and user-reserved decisions.

Do not ask again for resolved fields. A delegated field belongs to Agent judgment until the user changes it. `none`/explicit absence does not mean "fill this creatively later."

For persistent work, create a Project Manifest through `project-operability.md` before artifacts proliferate. `project-state.md` then owns durable persistence and change governance.

## 1. Core rule

Do not treat Chapter 1 as the place where consequential architecture is discovered by accident. Establish enough project state to make the opening honest **without pretending every long-form work needs the same planning artifacts**.

Readiness protects two distinct things:

1. **hard operability** - the opening must not depend on unknown facts, impossible access, contradictory state, unsupported research, or unresolved author-only decisions that block drafting;
2. **poetic operability** - the Writer must know what this project treats as salient, what counts as progression, what form/reader activity it protects, and what tempting optimizations it must avoid.

A project can be ready with low world complexity, no hidden causal network, no elaborate theme map, no endgame attractor, and no detailed timeline if those are not required by its causal risks or Project Poetics.

## 2. Base Readiness

Every substantial new project needs the **logical results** below. They may live in separate files or be compactly represented when the project is lean.

### 2.1 Project Brief

Owner: `front-loaded-adaptive-intake.md`.

Must make user-locked, delegated, absent/prohibited, and user-reserved decisions distinguishable.

### 2.2 Project Poetics

Owner: `project-poetics.md`.

Use `assets/prewriting-templates/project-poetics-template.md` when a persistent artifact is useful.

At minimum resolve provisionally:

- long-form organizing principle(s);
- legitimate salience sources;
- intended reader activity;
- what counts as progression;
- mind/explanation/form visibility constraints that matter now;
- do-not-optimize constraints;
- active poetics capabilities;
- any scoped authorized deviation already known.

Theme may be `none` or open.

### 2.3 Project Overview

Use `assets/prewriting-templates/01-project-overview-template.md`.

Record the novel promise and organizing principle(s) without forcing a single protagonist, dramatic problem, end-state attractor, mandatory transformation, or competing thematic positions.

### 2.4 Narrative Strategy

Use `assets/prewriting-templates/08-narrative-strategy-template.md`.

Derive POV/focalization, voice/form baseline, temporal resolution, description/dialogue/withholding, paragraph/cadence, and authorized heterogeneity from the current Project Poetics.

### 2.5 Chapter 1 Author Mission + Writer-safe derivative

Use `10-chapter-01-mission-template.md` and derive `assets/prewriting-templates/chapter-writer-mission-template.md`.

The mission must state the opening's **contribution/progression mode** rather than assuming a durable state delta. It may be event-driven, relational, epistemic, perceptual, recurrent, formally structured, or deliberately static.

### 2.6 Minimum causal/state slice

The project must have enough current state to draft safely. This is a logical requirement, not a fixed document count.

Depending on the project, the minimum slice may include only a few character/location/knowledge facts or may require full World/Timeline/Knowledge/Scene-Packet infrastructure.

Use `formalization-boundary.md` to stop when further structure no longer protects an actual risk.

## 3. Optional planning artifacts and activation

Existing templates remain available. Activate them only when the project actually needs them.

| Artifact | Activate when | Do not activate merely because... |
| --- | --- | --- |
| `02 World Model` | world systems, institutions, geography, material/social infrastructure, or offscreen autonomy constrain action/experience | "serious novels need worldbuilding" |
| `03 Character State` | durable body/resource/relation/knowledge/self-model state must persist | every named person needs an arc sheet |
| `04 Knowledge Topology` | actor/reader knowledge asymmetry, evidence, secrecy, focalization, deception, or fair-play inference matters | all fiction needs mystery machinery |
| `05 Hidden Causal Network` | adaptive hidden processes/opposition/counterfactual exposure matter | all worlds must contain a hidden conspiracy |
| `06 Long-Horizon Architecture` | long-distance inheritance or organization cannot safely remain implicit | every long novel needs an endgame ladder |
| `07 Reader Model` | memory, inference, familiarity, expectation learning, misunderstanding, or disclosure management materially constrains writing | every chapter must advance a question stack |
| `09 Timeline` | ordering, duration, travel, recovery, institutional delay, age/history, or synchronization is consequential | length alone implies a complex timeline |
| Scene Packets | time/place/access/custody/geometry are causally material in a planned scene | a scene's literary worth depends on packet bureaucracy |

Activation is orthogonal to governance profile. A lean project may activate a detailed Knowledge Topology; a forensic project may still leave theme or atmosphere unformalized.

Before declaring readiness, make an **explicit activation decision for every row in the table**. `inactive` needs a project-specific reason. This is an omission guard, not a demand to activate everything. Real-project evidence showed that an agent can otherwise build Timeline/Knowledge/Hidden-Cause artifacts, omit a causally central World Model, and still talk itself into readiness.

Record active optional artifacts in the Project Manifest when persistent project tooling needs to discover them. If a durable planning artifact exists and is being relied on, do not leave it undiscoverable merely because its file happens to be present.

## 4. Reality Grounding Layer

Identify real-world dependencies that materially constrain the opening or near causal chain: place, object, animal, custom, profession, institution, historical daily life, science, technology, law, infrastructure, ecology, etc.

Use `reality-grounding-research.md`. Research only what can constrain current architecture/prose. Do not postpone drafting to research remote trivia.

A factual dependency blocks readiness only when it is consequential to the opening and unsupported, scope-mismatched, materially contested without a project decision, or stale.

Research evidence does not choose Project Poetics.

## 5. Iteration passes

Run only affected passes; do not mechanically repeat a fixed sequence.

### Pass A - authority and poetics

Cross-check:

- Project Brief -> Project Poetics;
- Project Poetics -> Project Overview / Narrative Strategy;
- user exclusions -> do-not-optimize constraints;
- delegated choices -> actual project decisions;
- theme `none` / open decisions -> no accidental forced thesis.

Reject any capability that became active only because the Skill knows how to do it.

### Pass B - causal/state sufficiency

Cross-check the minimum state slice and any activated artifacts:

- time / travel / access / custody when material;
- capability costs and physical/resource limits when material;
- institutional authority when material;
- actor knowledge -> decisions;
- relationship history -> trust/refusal/risk;
- research facts -> adopted fictional constraints.

Do not create a rich simulation merely to satisfy a template.

### Pass C - reader/focalization sufficiency

When reader-state or knowledge asymmetry matters, cross-check:

- actor knowledge vs reader model;
- narrator/focalizer permission vs prose;
- what readers can plausibly retrieve, not just what was technically shown;
- familiarity/gist/expectation learning when these matter;
- literal hidden answers remain outside Writer-safe derivatives.

### Pass D - long-horizon sufficiency

When the project needs explicit long-horizon architecture, ask what actually organizes the long form:

- goals/endgame;
- accumulation;
- recurrence;
- social/historical drift;
- relation development;
- memory/temporal return;
- place;
- multiple centers;
- formal sequence;
- or a combination.

Do not overlock distant chapters.

Normal substantial Chapter 1 requires the complete first-volume chapter map and author-approved volume plan described in `long-horizon-architecture.md`. Dates/phase bands and reported mapped counts are insufficient. Volume 2 needs direction if it exists; later planned volumes need coarse functions/interfaces. A single continuous volume is valid when the author chooses it. Literary freedom, deliberate stasis, open interpretation, and local prose invention remain governed by Project Poetics.

### Pass E - opening integration

Cross-check Chapter 1 Mission against:

- current scoped Project Poetics;
- Narrative Strategy;
- minimum causal/state slice;
- activated reader/knowledge/world/timeline artifacts;
- research dependencies;
- explicit do-not-optimize constraints.

The opening is not required to showcase every project capability.

When Chapter 1 is meant to establish ordinary life, historical/social position, or a lived baseline, resolve a **Minimum Life Anchor** before drafting: the focal character's livelihood/social role, why they are here today, a concrete location anchor, and at least the minimum relationship/household fact needed by the scene (or an explicit reason that relationship is not applicable). Do not let the Writer invent durable biography accidentally while trying to start the scene.

### Pass F - Writer-safe handoff

Compile a Writer Mission and Writer Reader Brief only from permitted information. Include a Writer-safe scoped Project Poetics derivative: salience, progression mode, relevant mind/explanation threshold, form commitments, licensed recurrence, do-not-optimize constraints, and authorized local deviations.

Use `context-compilation.md` and semantic secret-taint controls. Negative spoilers remain spoilers.

Instantiate Scene Packets only for scenes whose spatial/custody/time/access state is causally material. When a Scene Packet is required because the scene contains the story's central causal mechanism (for example the first rewind, a custody transfer, an impossible-access test, or a forensic clue placement), close the transaction boundary **before** drafting: the trigger/entry state, reset or transfer semantics, relevant actors/objects, and Writer-visible packet derivative cannot remain “choose later.” Put causally required scene entries in the context request's `required_scene_ids` and `required_ids`; `scenes` alone is only a relevance hint.

### Pass G - adversarial review

Run only relevant attacks from `adversarial-review.md`:

- hard continuity/access/knowledge attacks;
- project-poetics consistency;
- accidental drift vs authorized variation;
- "helpful" overcorrection from another poetics;
- logistics/institution/opponent attacks only when those capabilities are active.

Propagate blockers to affected artifacts only.

## 6. Readiness gate

Use three explicit states:

- `BLOCKED` - at least one structural, evidence, authority, or handoff blocker remains.
- `REVIEW_READY` - architecture has converged enough for the author to review/approve the opening, but Writer authorization or final compiled handoff may still be pending. **Do not call this DRAFT_READY.**
- `DRAFT_READY` - author-required approvals are satisfied and the current Writer context has actually compiled from current-generation artifacts, with provenance/taint and semantic-kernel checks passing.

Declare **DRAFT_READY for Chapter 1** only when:

### Authority / openness

- no unresolved user-only decision blocks the opening;
- delegated and absent fields are represented correctly;
- consequential authorial uncertainty is explicitly open/provisional rather than silently resolved.

### Poetics

- a provisional or approved Project Poetics exists at sufficient resolution;
- the opening's salience/progression mode is intelligible;
- Narrative Strategy is derived from, not independent of, that poetics;
- known do-not-optimize constraints are explicit;
- any unusual formal deviation needed in Chapter 1 is authorized at the correct scope.

### Hard operability

- the minimum causal/state slice supports the opening;
- all activated artifacts are mutually compatible;
- required real-world dependencies are sufficiently grounded;
- knowledge/focalization legality is clear where relevant;
- time/travel/access/custody are validated where consequential;
- no validator is demanding an artifact or delta that the project never activated.

### Writer handoff

- Chapter 1 Author Mission exists;
- Writer Mission is sanitized;
- Writer Reader Brief exists when reader-state constraints matter;
- scoped Project Poetics is approved/active as required by project authority and the current Writer pack **actually compiles**;
- provenance closure and semantic secret-taint closure pass for the current context generation;
- causally required Scene Packets have closed pre-draft transactions and Writer-visible entries explicitly required by the context request;
- the compiled pack hash/manifest refer to the current context generation rather than a stale pre-revision pack.

Readiness does **not** mean the entire novel is solved, all themes are known, or every optional capability has been activated.

Run:

```bash
python scripts/storyctl.py readiness PROJECT_ROOT/project-manifest.json PROJECT_ROOT/planning/prewriting-readiness.json --root PROJECT_ROOT --json
```

A prose readiness review may explain the decision, but it cannot override a failing machine gate or substitute “should compile after approval” for a real `DRAFT_READY` compile.

## Evidence, review snapshots and CLI

Readiness `1.1.0` retains the three gate names. The `gate` field is a claim; `draft_permission: true` from a live formal check is the permission. A failed check returns effective `BLOCKED` and preserves `claimed_gate` for diagnosis. Diagnostic `--no-recompile` never grants permission and is rejected with `--require-draft-permission`, its `--require-draft-ready` alias, freeze/bind, or `--action start-chapter-1`.

`artifacts` separates maturity claims from evidence. Each required row has `ref`, `evidence_ref`, `status`, `sha256`, and `evidence_sha256`. Evidence is a project-relative JSON object binding `artifact_ref`, nonempty concrete `coverage`, and closed `open_items: []`. The checker validates structural Cast, World, volume, Mission, and Scene evidence in addition to byte hashes. It does not grade literary meaning. Base evidence covers Project Brief, Project Poetics, Narrative Strategy, Author Mission, Writer Mission, and Cast. Activated artifacts require current-cone evidence; historical dependencies additionally require snapshotted VERIFIED sources, scope and adopted constraints. Optional irrelevant World fields may use `{ "status": "NOT_APPLICABLE", "reason": "..." }`.

Assess `causal_risks` explicitly: `world_systems`, `time_loop_or_branch`, `historical_grounding`, `secret_asymmetry`. Neutral nulls and scaffold reasons block review. Time-loop/history/social-system risks activate World; time-loop risk also activates Scene/Timeline/Knowledge/Character protections. Live branch/revision subsystem sentinels prevent omitting World/Scene merely by declaring risk false. Mark only real risks; do not construct an encyclopedia. Cast and active current-cone World/Character/grounding evidence name nonempty `writer_entry_ids` resolving to eligible request-required safe derivatives. The Writer Mission must have matching chapter evidence, a `mission` entry, and `writer_handoff.mission_entry_id`; `required_writer_entry_ids` cannot be empty. Required scene records independently constrain `request.required_scene_ids` even if someone clears that request list.

Use the same interpreter for each command:

```bash
python scripts/storyctl.py readiness MANIFEST READINESS --root PROJECT_ROOT --action refresh --json
# Resolve blockers and regenerate the saved current Writer pack/manifest.
python scripts/storyctl.py readiness MANIFEST READINESS --root PROJECT_ROOT --action freeze --json
# Present the returned id, fingerprint and complete review payload to the author.
# Import the subsequent actual user-message approval into a project evidence file.
python scripts/storyctl.py readiness MANIFEST READINESS --root PROJECT_ROOT --action bind-approval --approval-evidence authority/approval.json --json
python scripts/storyctl.py readiness MANIFEST READINESS --root PROJECT_ROOT --require-draft-permission --json
```

`refresh` captures existing bytes, upgrades the representation, sets `BLOCKED` and clears both frozen snapshot and author approval. It never fills literary content, maturity, user messages, or structural choices. Re-run it after evidence changes, then recompile if context inputs changed. `freeze` checks current evidence and live handoff, sets `REVIEW_READY`, and emits a fresh snapshot ID plus deterministic fingerprint/payload. The fingerprint binds all readiness decisions/evidence, chapter, mode, request/index/source bytes (including backend provenance nodes), live manifest, current state, and checker/compiler versions. Only the permission transition of `gate` is normalized; all other claim changes drift. Campaign registration is bound independently of its mutable session ledger.

The imported approval JSON requires `source: "user"`, `action: "draft-approval"`, unique real `message_id`, positive conversation `message_order`, explicit `statement`, the presented `snapshot_id`, `review_fingerprint`, `target_chapter`, and `draft_mode`. `bind-approval` refuses a changed review or consumed approval ID. Refresh/refreeze cannot reuse old evidence: a new snapshot needs a new author message. Checks automatically invalidate effective permission when any bound content, structured evidence or declaration changes. They are read-only; no agent memory or manual invalidation is required.

This is an auditable transcript-attestation boundary, like the existing campaign protocol. Local files cannot cryptographically prove human authorship or good-faith review. Import real messages; agents must never synthesize approval/insistence/volume authority or rewrite imported messages to fit a new snapshot. Tests use explicitly synthetic TEST messages only.

Legacy `1.0.0` remains readable for diagnosis and carries a migration warning; it cannot grant formal permission. `--action refresh` safely upgrades the envelope but does not fabricate missing Cast/volume/maturity/approval evidence. Old Context Index/Story State/Runtime/campaign representations remain supported by their existing parsers. Old pack manifests can still be inspected, but must be regenerated to pass formal live metadata comparison. Legacy single-center Cast evidence can use `central_character`; new/ensemble evidence uses `narrative_centers[]` without a unique protagonist requirement.

## Two-request fragmentary override

The first request to write before remote volume depth is ready must receive a concrete refusal: identify missing architecture, explain why normal mode recommends finishing it, and stop without prose. The first request is never insistence. Only a later independent user message explicitly acknowledging that warning permits `draft_mode: "FRAGMENTARY_OVERRIDE"`.

Both imported user requests must bind the same `target_chapter`. Their order and the first message bytes remain part of the frozen provenance.

The `fragmentary_override` record names `warning_ref` and `insistence_ref`. The assistant warning binds the actual first request via `first_request_ref`, has `action: "refused"`, conversation `message_order`, current `target_chapter`, nonempty `missing_volume_items`, explicit `statement`, and `prose_generated: false`. The first imported user record has `action: "early-draft-request"`; later insistence has `action: "fragmentary-insistence"`, a different real `message_id`, a greater order than the warning, current chapter and exact `warning_sha256`. Same-message reuse fails.

Override waives only `validate_volumes`' remote architecture depth. Current World/Cast/Character, grounding, secret isolation, provenance, Semantic Kernel/Runtime, Writer Mission, scoped poetics, scene transaction, context compilation, live pack freshness and current author authorization all remain mandatory. Freeze/present/approve the fragmentary review too. Exploration is never naked drafting.

Formal safety delegates to the existing Story State validator and, when Runtime is active, Runtime schema and invariant validators as well as the Kernel. Current-cone research uses the existing freshness owner. With secret asymmetry active, a nonempty live Secret Registry must connect to actual protected source taint nodes; declared future-truth entries cannot rely on visibility alone. The review fingerprint includes Runtime file bytes and the schema/checker dependencies of these gates.

## 7. Discovery-writing exception

For a bounded exploratory branch/local task, use `discovery-drafting.md`. A substantial opening requested before its volume architecture is ready follows the two-message protocol below; neither `discovery_mode=true` nor a discovery label bypasses formal current-cone safety.

Project Poetics may be provisional and sparse. Draft-emergent patterns become **poetics hypotheses**, never automatic project-level commitments. Promote only after review/approval and propagate consequences through change control.

## 8. Handoff after Chapter 1

After drafting starts:

- Project Poetics remains live author/planning state under `project-state.md` governance;
- optional artifacts remain active only while their risks/capabilities remain relevant;
- new artifacts may be activated later without implying earlier planning failure;
- unused templates do not create Narrative Debt;
- chapter/arc poetics overrides may be added without rewriting the entire project;
- durable prose state is reconciled separately from literary interpretation.

The goal is **minimum sufficient architecture plus explicit project-specific poetics**, not completion of a universal form.
