## 1. Authority architecture

The functional layer map below remains useful, but it does **not** imply that every module has universal literary authority. Apply this ownership hierarchy first:

1. **Hard Core** - canon/user authority, semantic strata, causal/temporal/knowledge legality, state persistence, revision lineage, authorial openness, evidence/provenance, and formalization restraint.
2. **Meta-Core** - `literary-meta-core.md`; cross-poetics anti-collapse distinctions and evidence-boundary guardrails. It diagnoses category errors and never supplies a universal aesthetic target.
3. **Project Poetics** - `project-poetics.md`; canonical owner of project-specific salience, progression, reader activity, explanatory threshold, mind opacity, form visibility, licensed recurrence, do-not-optimize constraints, capability activation, and scoped authorized deviations.
4. **Selectable Poetics Capabilities** - strong but conditional modules such as thematic polyphony, hidden causal networks, autonomous social ecology, institutional negotiation, restraint/negative space, dynamic vividness, figurative systems, and other craft mechanisms. Knowing a capability does not activate it.
5. **Craft Execution** - selection, scene, rhythm, time, voice, focalization, dialogue, environment, paragraph, and prose modules consume the current scoped Project Poetics instead of defining the project's values independently.
6. **Infrastructure / Evaluation** - Runtime, Project State, Context Compilation, observability, tests, mutation/metamorphic/STC, and tooling protect operations and evaluate declared constructs without becoming a genre.

A module may sit in one functional layer below while having a different authority role above. For example, `hidden-causal-networks.md` remains Layer B by function but is a **selectable capability**, not a Hard-Core obligation.

## 4. Canonical lifecycle

For a serious new long-form project:

```text
Front-Loaded Adaptive Intake / Project Brief
        -> Project Manifest + governance profile
        -> provisional Project Poetics
        -> Reality Grounding Layer as needed
        -> Base Readiness artifacts + risk/poetics-activated artifacts
        -> cross-document convergence
        -> freeze/present evidence review -> fresh author approval -> live formal draft permission
        -> current scoped Project Poetics / authorized overrides
        -> current chapter mission
        -> optional Runtime Mode projection / active canon branch
        -> current Scene Packet entry snapshot
        -> role-scoped context pack
        -> prose
        -> optional/required prose-state reconciliation gate
        -> cross-layer semantic check when world/knowledge/reader/visibility/evidence layers interact
        -> Scene commit (append semantic runtime events first when active)
        -> Chapter commit (same write-side rule for durable chapter deltas)
        -> refresh projections / propagate dependency invalidation
        -> optional policy-triggered humanities sidecar
        -> optional user development decision
        -> affected documents / packets updated or invalidated
        -> next chapter mission
```

Ownership by stage:

- pre-work user intent / delegation / interruption policy -> `front-loaded-adaptive-intake.md`;
- cross-poetics guardrails -> `literary-meta-core.md`;
- project literary commitments / capability activation -> `project-poetics.md`;
- evidence -> `reality-grounding-research.md`;
- pre-draft convergence -> `prewriting-readiness.md`;
- scene spatial transaction -> `spatiotemporal-scene-state.md`;
- dramatic scene construction -> `scene-architecture.md`;
- durable project updates -> `project-state.md`;
- cross-layer semantic legality / derivation / preservation -> `narrative-semantics-kernel.md`;
- committed runtime history / branch lineage / dependency impact / Why Trace -> `narrative-runtime.md`;
- runtime representation upgrades -> `runtime-schema-migration.md`;
- deterministic project laws -> `narrative-invariants.md`;
- chapter revision impact -> `semantic-revision.md`;
- bodily/resource continuity -> `embodied-resource-state.md`;

- authorial OpenIssues / working hypotheses / resolution policy -> `open-issue-semantics.md`;

## 5. Canonical terminology

### Semantic-kernel family

- **semantic stratum** - the kind of claim an artifact makes: author/open design, committed semantic history, deterministic typed projection, actor epistemic state, reader exposure/model, information-flow policy, evidence/provenance, or analysis/governance.
- **story/valid time** - when something holds or happens inside the fictional world.
- **semantic commit time/order** - when the project durably accepts a semantic transition into history; Runtime branch `seq` is this order when Runtime Mode is active. Commitment does not by itself imply fictional canon.
- **discourse/exposure time** - when prose makes information available to the reader. It is neither story time nor commit order.
- **world update** - the fictional world changes.
- **epistemic update** - an actor learns, forgets, suspects, or revises belief without necessarily changing the world.
- **reader-exposure update** - prose changes what the reader has been shown.
- **policy update** - role visibility/declassification changes without erasing provenance.
- **representational revision** - project representation changes while intended story meaning is preserved.
- **authorial decision update** - the user/authorized delegate resolves, reopens, excludes, locks, or relaxes S0 design commitments without depicting an in-world occurrence.
- **OpenIssue** - a consequential S0 question whose authorial settlement is governed rather than silently filled.
- **position** - an issue-local candidate claim; its truth viability is separate from whether planning currently uses it.
- **working hypothesis** - a viable position temporarily used for conditional exploration; it does not narrow authorial truth.
- **commitment boundary** - Writer-safe derivative exposing what is fixed and what must remain uncommitted without exposing raw backend candidates.
- **branch intervention** - a counterfactual lineage shares committed prefix history, then changes selected interventions downstream.

### Runtime family

- **event** - immutable committed record of a consequential semantic transition plus its intent; its target stratum determines whether it is world canon, epistemic state, reader exposure, policy, authorial design, or analysis/governance history.
- **projection** - query-oriented current/past typed state derived from events; rebuildable when Runtime Mode is active, without gaining higher semantic authority merely because it is replayable.
- **snapshot** - cached projection at a known event point; optimization, not canonical history.
- **canon branch** - event lineage that shares parent history through a fork event, then diverges.
- **dependency edge** - `source -> target`, meaning target depends on source.
- **discovery** - draft-emergent possible fact not yet promoted to committed canon.
- **authorial unknown** - legacy/coarse term for author-level unsettled truth; use OpenIssue when consequential openness requires durable governance.
- **runtime schema version** - representation contract understood by runtime tooling; not a story-canon version.
- **event version** - semantic version of one event type's payload/meaning, normalized on read when required.
- **transaction** - proposed all-or-none append against an expected branch revision.
- **Narrative Debt** - known temporary weakness deliberately carried forward with an owner/resolution boundary; distinct from in-world consequence residue.

### State family

- **Project Brief** - normalized upstream record of user-locked, delegated, absent/prohibited, and user-reserved author-level intent before substantial execution.
- **Project Manifest** - project-level identity/recovery index pointing to canonical artifacts and governance profile; not fictional canon.
- **project format version** - version of the overall project representation/layout contract, distinct from Runtime schema version and story canon.
- **Resume Capsule** - regenerated Director-facing recovery summary derived from canonical artifacts; never a competing source of truth or a blind-Writer context.

- **state** - a currently true condition with future causal relevance.
- **delta** - meaningful change between states.
- **inertia** - forces/habits that make a state resist change.
- **residue** - what remains after change.
- **lag** - a layer that has not caught up with another changed layer.
- **rebound** - an old pattern reasserting after temporary change.
- **path dependence** - the route taken changes later possibilities/costs.

### Information family

- **semantic secret taint** - opaque provenance label carried by artifacts directly or transitively derived from protected backend truth until explicit role declassification.

Keep four questions separate:

1. **objective truth** - what is actually true;
2. **actor knowledge/belief** - what each person knows or thinks;
3. **camera permission** - what current narration may honestly reveal;
4. **reader state** - what the reader can currently retrieve, infer, or suspect.

### Process family

- **offscreen process** - any causally active process outside current page time.
- **hidden causal thread** - an offscreen process whose existence/objective/mechanism/significance is partly concealed and inferentially important.
- **background/neighbor process** - local material/social activity that may never become plot-critical.

Do not turn every background process into foreshadowing.

### Spatial family

- **spatial state** - time-indexed location/containment/relation/access truth.
- **reference frame** - the orientation system that gives a directional claim meaning.
- **Global Spatiotemporal World Graph** - durable nodes/edges and their time-indexed relations.
- **Scene Packet** - five-sheet local state bundle for one full persistent scene.
- **atomic scene commit** - synchronize all dependent local/global state before the scene becomes committed canon.

### Resolution family

- **descriptive resolution** - how much material/spatial attention a moment receives.
- **temporal resolution** - how much page time a span of story time receives.
- **semantic paragraph** - a local narrative grouping whose boundary signals continuation or reorganization of the reader's current event/discourse model.
- **display block** - optional presentation-only subdivision for a medium such as mobile reading; it must not silently redefine semantic paragraph structure.

These vary independently.

### Narrative-change family

- **scene delta** - local dramatic/material/interpretive change.
- **chapter movement** - how one or more scene deltas change pressure, feasibility, or reader question.
- **arc inheritance** - durable changed state later arcs must live with.

### Social-memory family

- **public version** - socially circulating account of an event, possibly partial or false.
- **reputation** - durable expectation that changes others' behavior.

A false public version can cause real effects without becoming objectively true.

## 6. Cross-reference discipline

Multi-regime diagnosis is owned by `project-poetics.md` at **Project Poetics -> Craft Architecture**, not Runtime truth. Its four-axis vocabulary identifies organizing pressure separately from mediation, closure and temporal form; specialist owners retain their existing execution responsibilities. No new owner-gap exception is needed: identifying long-form organizing principles was already its declared responsibility. `scripts/narrative_regime_qualification.py` is evaluation tooling under the existing behavioral-evaluation owner, not a literary engine.

When a local module needs a cross-cutting rule:

1. state only the local consequence;
2. point to the canonical owner;
3. do not reproduce the owner's full checklist;
4. do not create a near-synonym unless the distinction is real and documented here.

Project documents record **project-specific state**. Skill references define **how to reason**. Assets provide **reusable forms/templates**. Keep these three roles separate.

## 7. Maintenance rules

### Phase 0 architecture freeze (active)

Phase 0 freezes the **canonical reasoning-owner surface**, not implementation work. Repair, deepen, test, or refactor current owners freely; add scripts, schemas, assets, fixtures, and tests when they implement semantics that an existing owner already owns. Do not create a new reference or major literary subsystem merely because a topic is interesting, a paper suggests a new abstraction, or an existing owner is inconvenient.

Before proposing a new reference or major literary subsystem:

1. preserve a minimal reproducer for a concrete failure family;
2. identify the semantic stratum and list the existing owners that plausibly govern it;
3. try extension, clarification, a test/fixture, an asset/schema, or an implementation repair under the current owner first;
4. demonstrate why those owners cannot represent the failure without violating their declared semantics or creating a contradictory responsibility boundary;
5. obtain explicit author/governance approval for the owner gap before creating the new owner.

Do not evade the freeze by hiding a new literary ontology inside an existing owner. An owner may deepen only within the responsibility already declared in this map. New approved reference owners must be recorded as owner-gap exceptions in `assets/architecture-freeze.json` and then registered in this map in the same change. Pending or rejected proposals do not authorize new references.

`assets/architecture-freeze.json` is the machine-readable Phase 0 baseline. `scripts/audit_skill_structure.py` rejects unapproved additions to the Markdown reference directory. That check is intentionally narrower than the human rule: it can prove that the reference surface did not grow without an exception, but it cannot prove that an existing file did not smuggle in a new subsystem.

Before adding a new reference file after Phase 0 is lifted or through an approved exception, still ask:

- Is this a genuinely new responsibility or only an example/checklist for an existing owner?
- Could the material become an asset template instead of reasoning instructions?
- Could it become an optional example library instead of part of the active craft stack?
- Which current owner would lose or delegate responsibility?
- Does the split reduce normal context load?

Before adding a new regression test, ask whether an existing failure family can absorb it as a variant.

Before adding a new rule to `SKILL.md`, ask whether it belongs in an owner reference instead. Keep `SKILL.md` as control plane, not a second encyclopedia.

Use `test-tier-contract.md` to choose maintenance depth instead of assembling ad hoc mega-runs. Routine edits use Fast, normal promotion uses Core, stable releases/major architecture use Full, and only explicit high-cost reliability campaigns use Soak. Before packaging a maintained version, Full is the default internal release gate unless the change is demonstrably narrower; the official Skill validator/package validator still run separately. Also use `scripts/rule_entropy_audit.py` as a nonbinding maintenance diagnostic; exact long-paragraph duplication or rapid documentation growth is a reason to inspect ownership/pruning, not an automatic deletion order. Regression fixtures follow `assets/regression-corpora/README.md`: keep canonical/source or deliberately adversarial inputs and regenerate disposable outputs in tests.
